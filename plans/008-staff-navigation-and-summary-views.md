# Plan 008: Simplify staff navigation and client/referral summaries

Status: **IMPLEMENTED — approved October 3, completed on the feature branch October 4, 2026.** Reviewed against `54f5d58` on October 3, 2026. Navigation/summary effort M; account-payment effort L and higher backend risk. The approved staff views and transactional account-payment guards are included in PR #93.

## Intent and existing behavior

Standard staff need Collect Test, Quick Book, Test Tracker, Collect Payment, Clients, Courts and Employers. The super admin retains all existing operational, billing, CMS, user and technical navigation. Keep Payload's native sidebar, collapse control, groups and account controls. Do not introduce a secondary sidebar or replace `admin.components.Nav`.

The app pins Payload / @payloadcms/ui / @payloadcms/next to **3.90.2**. `src/payload.config.ts:189` already uses `beforeNavLinks` for Collect Test, Quick Book, Test Tracker and Referral Billing; custom root views are registered at `:200`. `Admins/index.ts:41` defines `admin` and `superAdmin`. Technicians is a scheduling-profile collection, not a separate authenticated technician role. These designs apply to staff signed in as a standard admin.

Clients (`index.ts:108`) and Courts/Employers (`index.ts:15`) already allow admin updates and reserve deletion for super admins. Preserve this. Basic edits include identity/contact/headshot, recipients and approved medication changes. Referral contacts/name and approved default-test edits remain available. Referral default-test changes have a linked-client synchronization hook, so retain its existing side effects and approval behavior. The proposed staff summary treats global invoice settings as advanced settings; the current referralBilling field access allows all admins to change them. Restricting those settings to super admins is a separate, explicit access change to review, not an existing permission being claimed here.

## Supported Payload mechanisms

Use collection/global `admin.hidden: ({ user }) => …` for role-dependent visibility only where staff do not need the native routes. `hidden` excludes navigation **and admin routes**, but is not API access control. Keep Clients, Courts and Employers visible so their native edit routes stay usable. Put them in native Collections / Referrals groups. `admin.group` supports a string or false, not a role callback.

Inventory native deep links before hiding other collections. In particular, `DrugTestTrackerClient.tsx:336` opens `/admin/collections/drug-tests/<id>`; the completed collection and client history also need test records. Do not role-hide DrugTests and break those routes. Where a collection must retain staff routes but should disappear from the menu, use `group:false` and add its super-admin-only entry through the supported `afterNavLinks` slot. That setting is global, so its automatic super-admin group entry is replaced by a link rather than preserved in the same position. Keep the native entry until this tradeoff and all deep links are verified. Apply the same review to PrivateMedia/headshot relationship controls. Do not reduce read access just to simplify navigation or invent a new test-detail view to compensate.

The four staff actions use the already-established `beforeNavLinks` extension slot. Keep existing Quick Book drawer behavior. Show Referral Billing and Analytics only to super admins in the proposal; custom links need explicit role checks. Inventory all registered collections, globals, dashboard widgets and custom views before configuring the role-dependent visibility. Do not equate hiding a link with denying the operation.

Add Summary document tabs to Clients, Courts and Employers using `admin.components.views.edit.summary`, preserving the native Edit tab. The repo already has this exact pattern in `src/collections/DrugTests/index.ts:49` and `views/DrugTestSummaryView.tsx`. Link staff search/list rows and collection-context actions to the summary. Do not replace the entire document root or delete the native editor. Keep list search useful with headshot/name/DOB/referral/client balance. Super-admin default routing may stay unchanged.

## Summary contents

- **Client:** headshot/identity/contact, referral, useful actions, medications, result recipients, complete paginated test history, report links, payment history, client-owned balance and account credit. Distinguish referral-owned balances rather than asking the client to pay them. Historical result expectations use the test's medication snapshot, not today's medication list. A collection awaiting lab results has no result/report link until a report exists. A negative result is labeled Negative, not Expected-negative.
- **Referral:** court/employer identity, contacts, preferred test, invoice eligibility, separate result contacts and billing email, linked clients and useful upcoming appointments/statuses. Basic Edit remains; no Delete. A payer exception for one test does not edit the referral's global invoicing setting.
- **Today:** appointments, collection/booking entry actions. No added Follow-up panel. Test Tracker remains the location for pending results/confirmations and existing follow-up functions.

Staff access and field permissions must be enforced on server endpoints/actions and native Edit forms as well as the summary UI. Custom views use the authenticated server principal and enforce collection/field access. Do not serialize unnecessary private fields to the browser. Do not widen access simply to make a hidden relationship selectable.

## Collect Payment contract — separate backend scope

The user requested a payment entry point independent of collecting a test. One native nav action opens a custom root view: select/search client, verify headshot and DOB, enter payment, review allocation, record, show receipt/outcome. No fake booking or test is created. From a client summary, open the same view with that client preselected. Money-only views do not show medications or test-result components.

Reuse `src/collections/Payments/services/applyPayment.ts:137` for the ledger, oldest eligible balance first, excess to account credit, and `withPayloadTransaction.ts` for transaction handling. Add an authenticated client-level action; do not create arbitrary Payments documents with a generic admin form. It must re-read balances, validate positive finite cents, enforce eligible client debt, and return canonical allocation/remaining-credit/receipt outcomes. Preserve payment receipts and audit identity; submissions/retries must not double post.

Plan 007's per-test payer resolver is a prerequisite for accurately allocating mixed client/referral debt. Current helpers exclude already invoiced tests but do not fully distinguish pre-invoice referral debt. Do not let account payments consume that debt. Showing a client balance must use the same eligibility rule as actual allocation.

Card collection requires additional reviewed work: `stripeTerminal.ts:226` currently requires a booking ID, and success reconciliation at `:618` also requires that booking. Do not fabricate a booking to reuse it, label a manual card record as a processed charge, or expose an unfinished reader flow. First reuse cash/credit safely; add an explicit account-payment Terminal contract and corresponding start/status/cancel/success/failure/idempotency tests before enabling card in this view. Optional additional account credit can stay collapsed. Show allocation details once, optionally in a disclosure.
